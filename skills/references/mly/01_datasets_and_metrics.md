# 数据集设置与评估指标（MLY 原书 Part 1-2，第 1-12 章）

> 本笔记用自有语言概括原书方法论要点，供 skill 使用时快速查阅；细节以原书为准。

## 1. 为什么先谈策略（第 1-4 章）

- 多数 ML 项目的时间不是花在写代码，而是花在"决定下一步做什么"。策略错误（比如盲目收集更多数据、盲目换模型架构）会让团队数月原地打转。
- **规模驱动机器学习进步**：过去十几年的经验是，在数据量和模型规模足够大时，"更多数据 + 更大模型"往往稳定优于精细的手工设计。这决定了：能用数据解决的问题，优先用数据解决。
- 但数据量的收益有前提——数据必须**与目标场景同分布**（见 [04 文档](./04_data_mismatch.md)）。

## 2. 开发集与测试集（第 5-8 章）

### 划分原则

| 原则 | 要点 | easymlops 落点 |
|------|------|---------------|
| 同分布 | dev 与 test 必须来自同一分布（同一时间段、同一客群、同一采集方式），否则指标噪声会让迭代失去方向 | 风控/续保场景：**按时间切分**（train 取早期、dev/test 取后期），见 playbooks/00 ① |
| 规模 | 现代数据量大时，不必再按 70/30 切；dev/test 只需"足够分辨指标差异"即可，通常占总量的 1%-10% | 大样本业务（百万级）测试集几万条通常足够 |
| 代表线上 | test 集分布要与上线后真实请求一致，而不是与训练数据易得的部分一致 | accept-only 样本偏差问题见 playbooks/00 ① checklist |

### 单一数字评估指标（第 8 章）

- 团队需要一个**单一数字**作为优化目标，多个方案才可快速比较（精确率 90%/召回 44% vs 精确率 92%/召回 40%，谁更好？没有单指标就没有答案）。
- 常用做法：精确率与召回率合成 **F1**；风控场景常用 AUC/KS 作为主指标；阈值处指标（召回@精确率≥x%）也满足"单数字"要求。
- easymlops 落点：`from easymlops.table.utils import calc_precision_recall_at_thresholds, calc_roc_at_thresholds`，先和业务约定主指标再开训。

### 优化指标与满足指标（第 9 章）

- **优化指标**（要尽量最大化/最小化的那一个数）+ **满足指标**（只要达到门槛即可，如延迟 ≤100ms、模型体积 ≤ 某值）。
- 典型组合：优化 F1，满足推理延迟约束；优化 AUC，满足 PSI 稳定性门槛。
- 这是在约束下的单指标化：有多个约束时不要加权平均成一个大杂烩指标，而是把约束固定为门槛。

## 3. 迭代闭环（第 10-12 章）

- dev set + 单指标的价值 = **迭代速度**：每个想法只需看一个数，几分钟内知道方向对错。
- **何时更换 dev/test 或指标**（第 11 章）：当你在 dev 上表现很好、但在真实业务（或 test）上持续不及预期时，说明 dev/test 或指标已偏离目标——及时更换，而不是继续在错误的标尺上刷分。
- 小结（第 12 章）：合理划分的 dev/test + 对齐业务的单一指标 = 整个项目的"指南针"。

## 4. 实操 checklist（结合本 skill）

- [ ] dev/test 同分布、同时间段；风控类任务 train 与 test 有时间先后（防泄漏）
- [ ] 与业务方确认单一优化指标 + 满足性约束（延迟/稳定性/合规）
- [ ] 基线系统先跑通（playbooks/00 ③），此后每次迭代只看主指标变化
- [ ] 定期检查：dev 上涨但线上/OOT 不涨 → 优先怀疑分布问题（转 [04 文档](./04_data_mismatch.md)），而不是继续调参
