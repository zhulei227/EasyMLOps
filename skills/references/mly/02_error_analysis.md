## 1. 先快速搭建第一个系统（第 13 章）

- **先搭一个快速但粗糙的端到端系统**（几条 pipe 串起来的基线），然后开始迭代。原因：只有端到端系统存在，才能做误差分析；误差分析结果才告诉你哪里最值得投入。
- 反模式：一上来在特征工程/某个模块上打磨数周，最后发现整个环节对最终指标贡献很小。
- easymlops 落点：playbooks/00_framework.md 的 ③ 基线模型（FixInput → FillNa → LabelEncoding → LGBM），先跑通再谈优化。

## 2. 误差分析怎么做（第 14-15 章）

核心动作：**人工查看开发集中模型判错的样本**，归纳错误的模式。

### 步骤

1. 用训练好的 pipeline 在 dev set 上跑 `transform`，收集预测错误（或业务损失大）的样本。
2. 逐条查看，按你猜测的失败原因**分桶计数**（如：缺失值占比高 / 类别特征未见组合 / 时间外推失效 / 标签本身可疑 / 边界样本）。
3. 每个桶统计占比，**占比高、可解决的桶**优先投入。

### 并行评估多个想法（第 15 章）

- 对同一批错误样本，用一张多列表格同时记录每个假设的适用情况（一个样本可同时命中多个假设），而不是"验证完一个假设再换一批样本"——一次查看、并行归因，极大省时间。
- 判断改进是否值得做：如果该类错误占 dev 错误的 ≥30%，修复它大约能改善错误率的三成；占 5% 则性价比可能很低（上限收益 = 该类错误占比 × 错误率）。

### easymlops 落点

```python
y_prob = table.transform(x_test)
err = x_test[(y_prob["1"] > 0.5) != y_test.values]  # 收集判错样本
# 人工/脚本分桶：按类别列、缺失模式、时间段切片统计占比
```

- 结合业务切片分析：按年龄段、渠道、客群维度看 bad rate 与模型错误分布，是风控 playbook 的标准动作。

## 3. 清理错标数据（第 16 章）

- 若 dev/test 中存在标注错误，要先**单独评估错标对 dev 和 test 的影响**：如果错标比例在两个集合上相近，其影响部分互相抵消，问题相对不致命；不对称时必须修。
- 检查分类器对错标样本的处理能力：深度/大容量模型（如 LGBM + 大量特征）可能把错标样本也"记住"，需专门看模型对错标样本的预测情况。
- 建议：训练集可容忍少量噪声，**dev/test 的标签质量要求更高**（它们是指南针）。
- 落点：给标签口径建 checklist（playbooks/00 ① 的业务方 checklist），错标样本单独登记复核。

## 4. Eyeball 与 Blackbox 开发集（第 17-18 章）

- 开发集很大时人工看不过来，**拆成两半**：
  - **Eyeball dev set**：需要人工逐条查看的部分，规模以"能看到足够多的错误样本"为准（如错误样本至少上百条，则该子集大小 ≈ 错误率倒数 × 目标错误样本数）。
  - **Blackbox dev set**：只用来算指标、不逐条看的部分，规模要足够大以保证指标估计可信（通常更大）。
- 用途区分：误差分析（人眼看）用 Eyeball 集；方案比较、报告指标用 Blackbox 集（或完整 dev/test）。避免"看了又拿来调"造成的信息泄漏。

## 5. 小结（第 19 章）

| 动作 | 目的 |
|------|------|
| 搭基线 | 让误差分析成为可能 |
| 分桶计数错误 | 找出占比最高的失败模式，按上限收益排序 |
| 多假设并行归因 | 一次看样本，同时验证多个想法 |
| 修错标（先评估影响） | 提高指南针的可信度 |
| Eyeball/Blackbox 拆分 | 人工分析与大样本指标互不干扰 |
