# 优化验证测试、端到端学习与分部件误差分析（MLY 原书 Part 8-10，第 44-57 章）

> 本笔记用自有语言概括原书方法论要点，供 skill 使用时快速查阅；细节以原书为准。

## 1. 优化验证测试（Optimization Verification test，第 44-46 章）

当系统输出"错误的答案"时，可能是两种完全不同的原因，处理手段也完全不同：

1. **优化问题**：搜索/优化过程没有找到目标函数的真正最优解（搜索算法、局部最优、计算资源）。
2. **目标问题**：目标函数本身打分不对——真实的最优解评分反而低于错误解（评分函数/模型缺陷）。

**判别方法**：构造一个测试，检查"真正的正确解"在评分函数下的得分是否优于系统给出的解。

- 若正确解得分**更差** → 目标函数有问题（模型/评分函数错了），去改模型。
- 若正确解得分**更好**，但系统没选它 → 优化过程有问题，去改搜索/优化算法。

- 一般形式（第 45 章）：比较 score(期望解) 与 score(实际解)，看问题出在"打分"还是"搜索"。强化学习场景同理（第 46 章）：区分是策略网络打分差，还是规划器没找到高分解。
- 落点：特征存储召回场景（Faiss 检索 + 精排打分，playbooks/04）——召回不准是"搜索"问题，精排分不准是"打分"问题，用上述测试区分后分别优化召回量或换精排模型。

## 2. 端到端学习 vs 多阶段流水线（第 47-52 章）

- **端到端**：原始输入直接映射到最终输出，中间不做人工分解。
- 趋势（第 47-48 章）：数据爆炸 + 深度学习让端到端在许多任务上成为可能；但**不是所有系统都适合**。

### 端到端的取舍（第 49 章）

| | 优点 | 缺点 |
|---|------|------|
| 端到端 | 数据说话，无人为偏见；无需设计中间组件 | 需要海量配对数据；排除了人工有用的先验 |
| 分阶段 | 中间组件可注入知识/规则；每步数据需求小；可解释、可局部修复 | 组件边界由人定，可能次优；误差级联 |

### 选择组件的两个标准（第 50-51 章）

1. **数据可得性**：每个组件的输入→输出配对数据是否容易获得？数据多的环节可端到端，数据缺的环节用规则/传统方法。例：拿到大量"原始输入→最终标签"但缺"中间环节标注"时，强行拆组件反而没数据训练。
2. **任务简单性**：组件的任务是否"简单到用适中数据就能学会"？把复杂问题分解成若干简单子任务，每步可靠，整体往往更稳。

- 直接学习丰富输出（第 52 章）：能拿到中间产物标注时，让模型直接输出更结构化的结果，往往优于只输出最终判别值。

### easymlops 场景对照

- 本项目 pipeline（清洗→编码→LGBM）本质是**分阶段路线**：中间件注入统计先验，数据需求小、可解释，适合业务表格场景（样本常在 1e4-1e6 量级）。
- 是否切到端到端（大模型直接吃原始字段）：仅在"目标输出标注量大且中间环节无标注价值"时考虑；风控类业务通常保留分阶段（合规可解释要求）。

## 3. 分部件误差分析（第 53-57 章）

多阶段系统的整体错误率无法直接告诉你**哪个部件最弱**。做法：

### 误差归因（第 53-55 章）

- 逐个部件替换成"完美版本"（ground truth / 人工标注的部件输出），看整体指标改善多少：

```
整体误差 = 100%
把部件1输出换成人工正确值 -> 误差降到 40%  => 部件1的上限收益 = 60 个百分点
把部件2输出换成正确值     -> 误差降到 90%  => 部件2的上限收益 = 10 个百分点
=> 优先优化部件1
```

- 一般情形（第 55 章）：部件输出是软性的（如概率、embedding）时，用"标准答案替换 + 对比指标"的思路近似归因。
- 与人类水平结合（第 56 章）：对每个部件问"该环节人类能做多好"，部件误差接近其人类水平时，说明该部件已接近天花板。

### 发现缺陷流水线（第 57 章）

- 危险信号：某个部件的输出在下游看来是错的，但该部件自己的指标是"好"的——通常意味着部件间训练目标错位（各自用不同分布/口径训练）。
- 处理：让相邻部件的评估口径统一（用下游真实期望评估上游），必要时让下游部件在上游真实输出（而非其训练分布）上重新训练。

### easymlops 落点

- 表格+NLP 双路 pipeline（playbooks/02、10）：分别测 NLP 支路与表格支路的单独准确率，再用 `Parallel` 合并后测整体，归因弱路。
- 召回（Faiss）+ 精排（LGBM）两段式：把召回结果换成人工标注的"全部正样本"，看精排指标上限，决定优化召回还是精排。
- 每条支路单独 save/load 测试，定位"加载后不一致"的部件（`auto_test` 一致性检查）。
